## Microphone findings and contract

The reported prepare-recovery error exists on the fetched base. `SetDeviceAsync`
used exact prior-name equality when looking up the driver, while its caller and
lease ownership checks accepted decorated WDM/MME names. The UI independently
looked up the prior driver with exact equality and guessed WDM on failure.
Neither algorithm handled ambiguity consistently. Saved `AutoMicrophoneStrip`
reuse also lacked an applied/prior-device ownership check.

`VoicemeeterDeviceIdentity` now parses only known complete presentation prefixes
(WDM, MME, KS, ASIO), trims whitespace, compares names case-insensitively, and
uses driver evidence to constrain resolution. One candidate resolves; zero is
unresolved; multiple candidates are ambiguous. No substring, similarity, or
partial-name matching is accepted for physical microphones. WDM remains the
explicit driver for new automatic assignments. A bare name present under more
than one driver cannot prove the prior driver and fails before a write.

Physical KS restoration is supported only when positively resolved. VB-Audio's
[Remote API manual](https://download.vb-audio.com/Download_CABLE/VoicemeeterRemoteAPI.pdf)
documents physical `Strip[i].device.ks` writes and selection by public name plus
type (pages 13 and 19). ASIO prior-strip recovery remains unsupported. The legacy
shared listening-output path retains its MME-only selection policy; output KS
is not added to that contract. That output selector's documented truncated-MME
name matching is intentionally distinct from complete microphone identity.

The microphone pipeline verifies saved ownership, reads device/A1/B1/gain,
persists leases before device/route/gain writes, verifies readback, saves config,
then validates the transaction's leases together before committing ownership.
Failed changes release only still-owned values in reverse order, retain uncertain
recovery records, and restore the previous configuration/selector. Outside
device or route changes are preserved. An additional expected-readback guard
checks the device again inside the bridge's operation gate. Setup's persisted
recovery validator accepts a positively recorded KS driver too.

## Visualizer findings and contract

The base selected a non-silent music strip before the physical listening meter.
That strip can be a separate game-feed copy; it does not describe the audible
direct MPV or YouTube leg. The old gate also did not directly require playing
state. This is a confirmed source-selection defect, not proof of the precise
cause of every stationary bar observed on the owner's installed copy.

The deterministic Core resolver receives topology, playing/switching state,
and available meter readings. Direct local/YouTube listening always uses the
selected Windows listening endpoint. If that meter is unavailable it returns
zero, because the independent game-feed strip is not a trustworthy fallback.
A verified mixer topology can use its active strip only when its physical
endpoint meter is unavailable. No current unsupported provider is presumed to
have such a verified path. Pause, loading/switching, unavailable topology, and
invalid measurements target zero. The 14 bars retain their geometry, quick
attack, slower decay, and Reduce Motion behavior. No synthetic motion or FFT
was introduced.

## Listening findings and contract

The base recorder starts after checkpoint recovery, observes once per second,
appends lifecycle facts, and checkpoints observed current intervals at about
30 seconds. `ReadAsync` already includes the current checkpoint and deduplicates
it against completed journal intervals. Restart reconciliation is not required
for current-session aggregation. No independent restart-only data defect was
confirmed; missing visible-page refresh is confirmed.

The page now refreshes on visibility, every 30 seconds while visible, and on
date-range changes. Its timer stops when hidden and during shutdown; the
independent one-second recorder remains unchanged. A UI-thread refresh gate
skips overlapping timer ticks and coalesces explicit requests. Aggregation runs
off the UI thread and discarded results do not update a hidden page. The manual
Listening Refresh button is replaced with a quiet automatic-update label.
Audio & Routing's manual device refresh and 15-second endpoint inventory refresh
are retained and do not follow Windows defaults during a session.

## Startup devices and migration

The typed `StartupAudioDeviceMode` defaults to `LastUsed`. An absent field in an
old configuration keeps this default; unknown numeric enum values normalize
to it. The additive field needs no destructive schema migration. The preference
saves immediately and applies at the next launch.

Windows Defaults uses NAudio Core Audio `GetDefaultAudioEndpoint` with
`Role.Multimedia` for both capture and render, once at launch. Multimedia is
chosen for this radio's normal media playback/recording selection rather than
Windows' separate communications preference. MMDevice IDs map to canonical
PnP endpoints by their stable complete endpoint GUID, never solely by friendly
name. Existing PnP discovery is an inventory, not default-device discovery.

Changed defaults use the existing transactional microphone and canonical
listening-player reconciliation paths. Unchanged IDs request no new device
assignment; unchanged gain also avoids a redundant write. Microphone changes
invalidate microphone evidence only; listening changes invalidate listening
evidence only. Independent music/game verification is retained. Voicemeeter and
WARDOGS virtual capture defaults are refused rather than fed back into a physical
strip. Unavailable/ambiguous devices, blocked recovery, and failed startup
mapping retain the old selection and expose targeted Needs Attention diagnostics.
Bluetooth microphone startup changes retain the previous selection until an
explicit manual confirmation, preserving the existing headset-quality safeguard.
